# strictler 스키마 — 확정 사항 정리

> 설계 논의 결과를 하나로 정리한 문서. **여기 적힌 것은 전부 확정**이고, 미결은 17절에만 있다.
> 폐기된 안과 그 이유는 16절 — **다시 꺼내지 말 것.**
> `CLAUDE.md` 는 이 내용의 요약본이고, 이 문서가 더 상세하다.
> 설계에 이르는 논의 과정은 `concept.md` 에 있다.

## 1. 네 층 = 네 파일

```
Spec (JSON)  →  Pipeline (JSON)  →  Node (JSON)  →  Script (.py)
   기획           DAG 구성           동작 정의        실제 동작
```

| 층 | 파일 | 담는 것 | 비유 |
|---|---|---|---|
| **Spec** | JSON | 어떤 파이프라인을 쓰는지 + 무엇을 보장하는지(intent) | 단위테스트 `describe` |
| **Pipeline** | JSON | 노드들의 DAG 구성 | Tekton `Task` |
| **Node** | JSON | **동작 정의** — 어떤 타입이고 어느 스크립트가 도는지 | Tekton `Step` |
| **Script** | `.py` | **실제 동작 코드** | — |

**노드와 스크립트는 별개 파일이다.** 노드는 *동작 정의*, 스크립트는 *실제로 동작할 코드*.

⚠ **노드 파일이 작은 것은 설계다.** 역할에 따라 분리한 결과이지 빈 자리가 아니다.
"얇으니 뭔가 더 넣어야 하지 않나"는 잘못된 문제 설정 — 넣을 이유가 생기기 전에 넣지 않는다.

### 무엇이 어디에 사는가 — 선언/사용 분리가 파일 경계와 겹친다

| | 어디 | 성격 |
|---|---|---|
| `type`, `script` 경로, `description` | **노드 JSON** | 동작 정의 |
| `Args`(= 입력·파라미터·필요 상태 선언), 출력 타입 | **스크립트** | **능력 선언** — *"이거 허용해주세요"* |
| `inputs`, `params`, `states` 매핑, `when` | **파이프라인** | **사용 선언** — *"내 검사에선 이거 쓸겁니다"* |
| `config` 값, `tool` 경로 | **Spec** | 이 검사에서의 실제 값 |

**통일하지 않는다.** 스크립트가 인자를 3개 받을 수 있어도 어떤 Spec 은 2개만 쓸 수 있다.
`${config.X}` 라는 **참조 문법만 공유**하고, 선언 층과 사용 층은 별개다.
상태 이름 매핑은 또 다른 층이다 — 값이 아니라 **파이프라인 상태 집합에 대한 이름 매핑**.

### 노드 재사용은 근본 동작

노드가 별개 파일이므로 **파이프라인이 노드를 참조**한다.
→ 재사용은 별도 기능이 아니다. 반복되는 체인은 노드를 참조하면 그만이고,
   **서브그래프 재사용 문법 같은 것을 둘 이유가 없다.**

## 2. 등록소 — strictler 가 파일을 관리한다

**스크립트 / 라이브러리 / 노드 / 파이프라인 / Spec 다섯 다 strictler 에 등록한다.**
등록하면 strictler 가 쓰는 폴더 아래로 **파일이 복사되어 저장**된다.

```
$STRICTLER_HOME/                    (기본 ~/.strictler)
  registry.json                     인덱스 — id · 이름 · 종류 · 해시 · 등록시각 · 참조
  scripts/    sc_a1b2c3d4.py
  libraries/  lb_9f8e7d6c.py
  nodes/      nd_e5f6a7b8.json
  pipelines/  pl_c9d0e1f2.json
  specs/      sp_3a4b5c6d.json
```

**사용자는 파일을 만들어 등록한 뒤 원본을 지워도 된다.** 복사본이 등록소에 있다.

### 해시를 함께 저장한다

등록 시 파일 내용의 해시를 같이 저장하고, **실행 시 복사본의 해시를 재계산해 대조**한다.

→ 목적: **정적 검사 루트를 피해 등록소 파일을 직접 고치는 "오류 가능성"을 막는다.**
   검사를 통과한 그 내용 그대로인지가 보장되어야 등록의 의미가 있다.

### id 로 참조한다

**등록 시 "이름"을 적지만, 참조는 이름이 아니라 자동 발급된 id 로 한다.**

| 종류 | id 접두 | 예 |
|---|---|---|
| 스크립트 | `sc_` | `sc_a1b2c3d4` |
| 라이브러리 | `lb_` | `lb_9f8e7d6c` |
| 노드 | `nd_` | `nd_e5f6a7b8` |
| 파이프라인 | `pl_` | `pl_c9d0e1f2` |
| Spec | `sp_` | `sp_3a4b5c6d` |

**참조 문법은 `${ref.<id>}`.** 네임스페이스는 하나면 되고, **종류는 id 접두가 말해준다** —
그래서 `${ref.pl_...}` 를 노드 자리에 쓰면 로드 시점에 잡힌다.

```jsonc
// 노드
{ "type": "perceive", "script": "${ref.sc_a1b2c3d4}" }

// 파이프라인
{ "id": "detectButtons", "source": "${ref.nd_e5f6a7b8}", "inputs": { … } }
```

⚠ 이전에 `@` 문법이 있었던 것이 아니다. 참조 문법은 `${env.X}` / `${config.X}` / `${state.X}` 뿐이었고,
**`${ref.<id>}` 는 등록소와 함께 새로 생긴 것**이다. 네임스페이스 강제 원칙을 그대로 따른다.

### 경로 참조도 여전히 가능하지만 비싸다

Spec 등에 절대경로를 그대로 적을 수 있다. 대신 **실행 시점에 "검증되지 않은 파일들"을 전수 검사**해야 한다.

**등록된 것은 해시만 그대로면 이미 검증을 통과한 파일이므로 다시 검사할 필요가 없다.**
→ 등록은 편의 기능이 아니라 **검증 결과를 재사용하는 기제**다.

### 수정은 id 를 유지한다

**`update` 는 같은 id 에 내용을 갈아끼운다.** 새 내용이 정적 검사를 통과해야 수정이 성사되고,
해시가 갱신된다. **id 가 유지되므로 참조가 안 깨진다** — 이게 수정을 두는 이유다.

⚠ **수정의 비용은 참조가 아니라 검증에 있다.**
삭제는 참조가 없어져 눈에 보이지만, **수정은 참조가 멀쩡한 채로 검증만 조용히 무효화된다.**
스크립트를 고쳐 출력 타입이 바뀌면 노드도 참조도 멀쩡하지만, 그 노드를 쓰는 파이프라인의
`input 정의 == output 정의` 검사는 이제 통과하지 않는다. 등록 당시엔 통과했는데도.

→ **수정 시 그것을 참조하는 상위를 전이적으로 재검증한다.**
  `registry.json` 이 참조 그래프를 갖고 있으므로 역방향 추적이 된다.
  (스크립트 수정 → 노드 → 파이프라인 → Spec 순으로 올라간다)

### 깨짐은 막지 않고 표시한다 — 두 종류

**삭제도 수정도 막지 않는다.** 참조가 있어도, 상위 재검증이 실패해도 진행된다.
대신 **목록 조회에서 깨진 구성을 드러낸다.**

| 깨짐 | 원인 | 규칙 |
|---|---|---|
| **참조 깨짐** | 참조 대상이 **삭제**됐다 | `STR-REG-004` |
| **검증 깨짐** | 참조 대상이 **수정**되어 상위 검증이 더는 통과하지 않는다 | `STR-REG-005` |

```
$ strictler pipeline list
pl_c9d0e1f2  login-flow   ✕ 검증 깨짐 — nd_e5f6a7b8 수정으로 STR-TYPE-004
pl_7f8a9b0c  menu-check   ✕ 참조 깨짐 — nd_1a2b3c4d 없음
pl_5e6f7a8b  cart-flow    ○
```

**막지 않는 이유:** 거부하면 교착이 생긴다 — 하위를 고치려면 상위를 먼저 고쳐야 하는데
상위는 하위 때문에 못 고친다. 그리고 **깨진 상태도 정상적으로 보고되는 결과**라는
lint 사고방식(9절)과 일관된다.

### 등록소는 프로젝트마다 따로 둔다

위치는 **`$STRICTLER_HOME`** 또는 **`--home`** 으로 정한다. 기본값은 `~/.strictler` 지만
**실사용에서는 프로젝트마다 하나씩 두는 것이 정본이다.**

```
export STRICTLER_HOME=$PROJECT_ROOT/.strictler   # 프로젝트에 두고 커밋한다
```

- 등록소가 다르면 **완전히 별개다** — 같은 파일을 두 등록소에 넣어도 id 가 따로 발급되고
  이름이 겹쳐도 섞이지 않는다
- **cwd 를 거슬러 올라가며 찾는 자동 탐색은 하지 않는다.** 3절의 *"상대 경로 금지 → cwd 의존성이
  사라진다"* 와 정면으로 어긋나기 때문이다. **이식성은 여기서도 환경변수가 담당한다** —
  `STRICTLER_HOME` 은 등록소에 대해 `${env.PROJECT_ROOT}` 와 같은 자리다
- 상대 경로를 주면 **에러**다. 경로 규칙은 등록소에도 똑같이 걸린다
- 등록소를 프로젝트 안에 두면 **검증된 파일 묶음이 레포와 함께 이동한다**

**어느 등록소를 쓰고 있는지는 항상 출력에 드러나야 한다.** `STRICTLER_HOME` 을 깜빡하고
전역 등록소에 조용히 쓰는 것이 가장 흔한 사고다.

### ★ id 는 재현되지 않는다 — ref 는 로컬, 경로는 이식 가능

id 는 등록할 때 무작위로 발급된다. **같은 파일을 다른 머신에서 다시 등록하면 다른 id 가 나온다.**

내용 해시에서 id 를 뽑으면 재현되겠지만, 그러면 *"수정은 id 를 유지한다 — 참조가 안 깨진다"* 가
무너진다. 내용이 바뀔 때마다 id 가 바뀌기 때문이다. **그 길은 막혀 있다.**

| 참조 방식 | 성질 |
|---|---|
| `${ref.<id>}` | **등록소 로컬.** 재검사를 건너뛸 수 있어 빠르다. **커밋해서 옮길 수 없다** |
| 절대 경로 + `${env.X}` | **이식 가능.** 레포에 커밋된다. 대신 실행 시점에 재검사한다 |

→ **둘 다 지원한다. 어느 쪽을 쓸지는 사용자가 고른다.** 레포에 커밋할 파일은 경로로 쓰고,
  로컬에서 빠르게 돌릴 때 ref 로 바꾼다. 이 성질은 **라이브러리 참조에도 똑같이 적용된다.**

### CLI 표면 — 종류 다섯에 CRUD 가 완전하다

```
strictler <종류> add | list | show | update | remove
```

`<종류>` = `script` / `library` / `node` / `pipeline` / `spec`.

| 명령 | 하는 일 |
|---|---|
| `strictler <종류> add <파일>` | 정적 검사 후 등록. **통과해야 저장된다.** id 발급 |
| `strictler <종류> list` | 목록. **깨진 구성 표시** |
| `strictler <종류> show <id>` | 상세 — 내용·해시·참조 관계 |
| `strictler <종류> update <id> <파일>` | 내용 교체. **id 유지.** 상위 전이적 재검증 |
| `strictler <종류> remove <id>` | 삭제. 참조가 있어도 막지 않는다 |

실행 계열은 따로 선다:

| 명령 | 하는 일 |
|---|---|
| `strictler node test <id>` | 노드 단위테스트 (실제 실행) |
| `strictler check <spec-id>` | 검사 실행 |

```
strictler script  add    ./detect_buttons.py
strictler node    update nd_e5f6a7b8 ./detect_buttons.json
strictler pipeline list
strictler spec    show   sp_3a4b5c6d
```

**CLI 가 유일한 표면이다.** AI 가 쓰고 등록하면 그 자리에서 걸리는 것이 저작 루프의 핵심인데,
그건 `add` 가 **규칙 id + 자연어 가이드 + 종료 코드 `2`** 를 돌려주는 것으로 이미 성립한다.

## 3. Spec

```jsonc
// specs/login.json
{
  "info": { "description": "이 파일이 무엇을 검사하는지", "version": "..." },

  "tool": {                        // 외부 도구 호출 경로 전체 — 경로 + 허용 함수
    "playwright": { "path": "${env.HOME}/.playwright/playwright", "functions": ["launch"] },
    "node":       { "path": "/usr/bin/node", "functions": [] }
  },

  "plan": [
    {
      "source": "${env.PROJECT_ROOT}/pipelines/login-flow.json",
      "description": "이거 뭐하려고 한건지",        // 항목별 의도 (단위테스트의 it)
      "config": { "loginUrl": "https://...", "expectedFields": 2 }
    }
  ]
}
```

- `info` — `describe` 에 해당하는 메타
- `tool` — 6절 참조. 경로만이 아니라 **허용 함수도 적는다**
- `plan` — 파이프라인 목록. **무조건 참조. 인라인 금지**
- 비교 파이프라인을 참조하는 항목은 `report` 필수 (12절)

### 경로 규칙 — 무조건 절대 경로

```
`~` 전개  →  환경변수 전개  →  `~` 재전개  →  결과가 절대 경로 스타일이 아니면  →  무조건 에러
```

- 상대 경로 금지 → **cwd 의존성이 사라진다**
- 이식성은 환경변수가 담당 — 머신·CI 마다 값만 다르고 Spec 은 그대로 커밋된다
- 환경변수 값 자체가 상대 경로여도 잡힌다 (`PROJECT_ROOT=./foo` → 에러)
- **`~` 는 허용** — cwd 와 무관하게 홈으로 결정되는 규약이므로 전개하면 절대 경로다.
  `${env.HOME}` 의 설탕 문법 (`os.path.expanduser()` 가 `~`·`~user` 처리)
- **★ 환경변수 값 안의 `~` 도 전개한다.** `PROJECT_ROOT=~/proj` 는 흔한 설정이고,
  `~` 를 허용한 논리("cwd 와 무관하게 홈으로 결정된다")가 여기에도 그대로 적용된다.
  → 그래서 전개가 **`~` → env → `~` 재전개** 3단계다. 전개는 고정점까지 반복해도 무방하다.
  이걸 빠뜨리면 앞자리(`${env.R}/x`)는 "상대경로입니다" 오진단이 되고,
  중간자리(`/srv/${env.S}/x`)는 리터럴 `~` 가 박힌 `/srv/~/proj/x` 가 **조용히 통과**한다.
- **전개 후 `${` 가 남아 있으면 에러다.** 경로 해석 시점엔 모든 참조가 풀려 있어야 한다.
  남은 `${` 를 리터럴 경로 조각으로 통과시키면 나중에 "파일 없음"으로 원인이 뭉개진다.
  닫히지 않은 `${` (예: `/opt/${env.HOME/x`) 도 같은 이유로 에러다.

### 참조 문법 — 네임스페이스 강제

**`${env.X}` / `${config.X}` / `${state.X}` / `${ref.<id>}`.**

같은 자리(`script`)에 환경변수와 config 가 둘 다 올 수 있으므로 구분이 필요하다.
네임스페이스가 없으면 `${BUTTONSCRIPT}` 를 봤을 때 **"미정의 환경변수"인지 "config 오타"인지 구분 못 해**
에러가 뭉개진다. **그 에러를 읽는 주체가 AI 이므로 정밀해야 한다.**

## 4. Pipeline

```jsonc
// pipelines/login-flow.json
{
  "info": {
    "name": "login-flow",
    "description": "로그인 페이지가 기획대로 동작하는지",
    "kind": "verify"                    // "verify" (값 검증) | "compare" (비교)
  },

  "config": { /* 변수 선언 — Spec 이 값을 채운다 */ },
  "states": { /* 상태 집합과 초기값 */ },
  "transitions": [ /* 전이 규칙 — 런타임이 수행 */ ],
  "nodes": [ /* 노드 참조 + 배선 = DAG */ ]
}
```

`kind` 가 최상위인 이유: Spec 의 `plan` 항목 필수 필드가 종류에 따라 달라지므로
(비교 파이프라인은 `report` 필수) **로드 시점에 가장 먼저 알아야 한다.**

### `config` — 변수 선언

```jsonc
"config": {
  "loginUrl":       { "type": "str", "required": true,  "description": "로그인 페이지 URL" },
  "expectedFields": { "type": "int", "required": true,  "description": "폼에 있어야 할 입력 필드 수" },
  "settleMs":       { "type": "int", "required": false, "default": 2000 },
  "buttonScript":   { "type": "str", "required": true,  "path": true }
}
```

파이프라인이 **선언**하고 Spec 이 **값을 채운다.** `description` 은 AI 가 Spec 을 쓸 때 읽는 설명이다.

**`type` 은 7절의 primitive 집합과 같은 어휘를 쓴다** — `str` `int` `float` `bool` `bytes` `list[T]`.
타입 어휘를 두 벌 두지 않는다.

**`path: true` 는 타입이 아니라 검증 속성이다.** 경로냐 아니냐는 값의 타입이 아니라
**경로 규칙(절대경로·환경변수 전개)을 적용할지**의 문제이므로 별도 플래그로 뺀다.

### `nodes` — 노드 참조 + 배선

```jsonc
{
  "id": "detectButtons",
  "source": "${env.PROJECT_ROOT}/nodes/detect_buttons.json",   // 노드 파일

  "inputs": { "html": "captureHtml" },                  // 스크립트가 받을 이름 : 노드 id
  "params": { "expected": "${config.expectedFields}" },

  "states": { "active": "capturing" },                  // 스크립트 어휘 → 파이프라인 상태 이름
  "when":   { "state": "active" }                       // 실행 조건 (스크립트 어휘로 쓴다)
}
```

| 필드 | 내용 |
|---|---|
| `id` | DAG 에서 참조되는 이름 |
| `source` | **노드 파일 경로.** 절대경로 규칙 적용 |
| `inputs` | **이름 붙은 다중 입력.** DAG 엣지가 여기서 나온다 |
| `params` | 스크립트에 넘길 값. `config` 참조로 기댓값 주입 |
| `states` | **노드 어휘 → 파이프라인 상태 이름 매핑.** 노드 재사용의 핵심 |
| `when` | 실행 조건. **노드 자기 어휘로 쓴다** — 파이프라인 상태 이름을 몰라도 된다 |

**`inputs` 가 DAG 를 만든다.** 별도 `edges` 섹션이 없다 — 입력 참조가 곧 의존 관계다.
**`type` 은 여기 없다.** 노드의 성질이지 사용처의 성질이 아니므로 노드 파일에 있다.

## 5. Node

```jsonc
// nodes/detect_buttons.json
{
  "info": { "name": "detect-buttons", "description": "무엇이 버튼인지 판정한다" },
  "type": "perceive",                                          // 다섯 노드 타입
  "script": "${env.PROJECT_ROOT}/scripts/detect_buttons.py"
}
```

| 노드 타입 | 산출물 | 하는 일 |
|---|---|---|
| **Vantage** | `Scene` | 어디서 볼 것인가 — 관측 지점·대상 확보 |
| **Sense** | `Sensum` | 감각 입력 — 해석 없는 원시 데이터 |
| **Perceive** | `Percept` | 지각 — 의미 부여 |
| **Reckon** | `Verdict` | 판정 — 기획과 대조 |
| **Action** | (input 그대로) | **행위** — 클릭·입력. 직교 노드 |

타입별 스크립트 검사기는 **노드 파일의 `type` 을 보고** 그 스크립트를 검증한다.

### Action 은 특수 노드 — input == output

```
X ──▶ Action ──▶ Y        실은 X ──▶ Y 인데 그 사이에 Action 이 낀 형상
      (클릭)
```

**Action 의 상단과 하단은 하나의 노드다.** Action 은 중간에 끼어 **부작용만** 일으키고
데이터 변환은 하지 않는다. `Args.input` 타입 == `returnResult()` 반환 타입.

→ 타입 검사 관점에서 **Action 은 투명**하다. 끼워 넣어도 X 와 Y 의 계약이 그대로 유지된다.
   그래서 "노드 사이 어디에나 끼워 넣는다"가 타입 체계와 충돌 없이 성립한다.
→ 클릭 **결과**를 후속 노드가 알아야 하면 **후속 Sense 가 다시 관측**한다.

### 구간형 Sense = Sense 두 개

"API 캡처 시작 … 종료"는 **시작 Sense 와 종료 Sense, 두 노드**다.
**그 안에서 뭐가 이루어지는지 엔진은 관여하지 않는다** — playwright 가 뭘 하는지 엔진은 모른다.

- **Sense 는 서로 선형으로 이어질 수 있다.** Sense → Sense 연결이 정상이다.
- 시작 Sense 는 playwright 의 **참조 정보**를 반환한다.
- 종료 Sense 는 **외부의 특정 조건**을 걸고 있다.

→ 특수 문법이 필요한 게 아니라 **그냥 일반 노드 둘**이다. `returnResult()` 는 언제나 1회.

## 6. Script — 노드 계약

### 진입점·출력 함수는 이름이 고정이다

| | 이름 | 규칙 |
|---|---|---|
| 진입점 | `runNode(args)` | **전 노드 타입 공통.** `args` 의 타입은 dataclass **`Args`** |
| 출력 | `returnResult()` | 반환 타입은 dataclass. **이름은 자유** |

**`Args` 라는 이름의 dataclass 를 선언하지 않으면 그냥 오류다.**
반환 타입 이름을 고정하지 않는 것은 **구조로 매칭**하기 때문이고(7절),
`Args` 만 고정인 것은 **엔진이 찾아야 하기 때문**이다.

### `Args` 의 내용물 — 세 필드로 출처를 나눈다

```python
@dataclass
class Args:
    input:  SomeInputType      # 앞단 노드들의 출력    ← DAG 가 준다
    params: SomeParamsType     # Spec 이 채운 값       ← Spec 이 준다
    state:  SomeStateType      # 참조할 파이프라인 상태 ← 런타임이 준다
```

평평하게 펼치지 않는다. 셋은 주는 주체가 다르다.

**세 필드는 쓰는 것만 선언한다.** 입력이 없는 Vantage 는 `input` 필드를 아예 두지 않는다.
없는 것을 빈 껍데기로 채우지 않는다 — `Optional` 금지의 취지와 같다.

⚠ **`Args.state` 가 곧 "필요 상태 선언"이다.** 별도의 `need_state` 배열 같은 것은 없다 —
`Args.state` 의 **필드 이름이 그대로 노드가 요구하는 상태 이름**이고,
파이프라인의 노드 `states` 가 그 이름들을 실제 파이프라인 상태로 매핑한다.

### Reckon 의 형식 요구 — 노드 타입별로 갈리는 유일한 검사

**Reckon 의 `Args.params` 는 기댓값 필드를 반드시 가져야 한다.**

스크립트에 기댓값을 하드코딩하면 **기획 파일이 껍데기가 되고**, 기획을 고쳐도 판정이 안 바뀌며,
"같은 기획을 A/B 에 돌린다"가 성립하지 않고, "기획대로면 통과"라는 정의 자체가 무너진다.
**형식 제한이 그 자리를 없앤다.**

### 외부 참조 — `Args.state` 로 선언한 것만

- 통제 대상은 **"엔진 내부의, 스크립트 외부 참조"** 뿐이다.
- 스크립트는 `Args.state` 에 자기가 참조할 것을 **미리 선언**해야 한다. 선언에 없는 것을 쓰면 **에러**.
- 파이프라인의 노드 `states` 매핑이 이 이름들을 실제 파이프라인 상태로 연결한다.

**그 밖의 외부 참조는 스크립트가 알아서 할 일이다.** 파일을 써놓고 나중에 읽는 건 강제할 방법이 없다.

### ★ 노드 내부는 input / output 만 맞추면 된다

**내부에서 AI 를 부르든 파일을 읽든 네트워크를 타든 엔진은 관여하지 않는다.**

**순수함수는 강제하지 않는다** — 순수성이라는 개념 자체를 두지 않는다.
AI 를 껴서 output 을 잘못 내놓으면 **타입 계약에 걸려 그냥 에러**다. 그걸로 충분하다.

### 금지 목록 — 전 노드 균일

| 금지 | 이유 |
|---|---|
| **시간 의존** | 실행 시각은 엔진이 state 로 준다 (8절) |
| **랜덤** | 같은 이유 |
| **직접 subprocess 호출** | `subprocess.run` / `exec` 류. **`tool` 선언분은 예외** |
| **미선언 state 참조** | `Args.state` 에 없는 것을 쓰면 에러 |

**그 외에는 아무것도 금지하지 않는다.** 파일 IO·네트워크·환경변수 전부 자유다.

### 스크립트의 의존성 — 격리하지 않는다. strictler 환경을 공유한다

**노드 스크립트는 strictler 와 같은 프로세스에 로드된다.** 그래서 스크립트의 `import` 는
**strictler 가 설치된 환경**에서 풀린다. 스크립트가 외부 패키지를 쓰면 그쪽에 함께 깔아야 한다.

```
uv tool install strictler --with selectolax
```

**이게 lint 의 표준 실행 모델이다.** ESLint 플러그인의 의존성은 ESLint 와 같은
`node_modules` 에서 풀리고, vite 플러그인·jest transform 도 같다. 9절이 채택한
*"사용자 코드를 그냥 로드해 실행한다"* 는 신뢰 모델과 **같은 결정의 다른 면**이다.

**PEP 723 헤더는 선언일 뿐 격리를 만들지 않는다.** 엔진은 헤더를 읽어 **등록 시점에
`import` 가능한지 확인**하고, 안 되면 규칙으로 잡아 설치 명령을 안내한다. 그것뿐이다 —
헤더를 보고 환경을 만들어 주지는 않는다.

**스크립트마다 `uv run --script` 로 격리 프로세스를 띄우는 안은 채택하지 않았다.** 이유는
비용이 아니라 **일관성**이다 — 그렇게 하면 lint 중에서 strictler 만 혼자 튄다. 게다가
의존성이 갈리는 단위는 스크립트가 아니라 **프로젝트**고, 그건 이미 `uv` 가 푸는 문제다.

→ **뒤집을 조건은 하나다.** 등록소에 **같은 패키지의 호환되지 않는 버전을 요구하는
스크립트가 둘 이상** 생기면 그때 격리를 만든다. 등록 시점에 선언된 의존성을 기록하므로
**그 조건은 도구가 스스로 검출한다** — 사람이 눈치채길 기다리지 않는다.

### `tool` — 외부 도구 호출 경로 전체를 관리한다

`tool` 은 경로 맵이 아니다. **허용 함수도 같이 적는다.**

```python
launch("${env.HOME}/.playwright/playwright")   # 함수명 ○ + 실행파일 경로 ○ → 통과
launch("/usr/bin/whatever")                    # 경로가 tool 에 없음 → 에러
run_shell("...")                               # 함수명이 tool 에 없음 → 에러
```

**검사 강도는 얕다** — 함수 호출 형태 전체를 정의하는 게 아니라
**함수명 + 그 인자로 적힌 실행파일 경로**를 매칭하는 정도다.
인자 전체를 검증하려 들면 strictler 가 외부 도구의 API 를 알아야 하고,
그건 **"외부 도구는 철저히 외부로 분리한다"를 깬다.**

**`tool` 에 선언된 것이 부가적으로 subprocess 를 띄우는 건 막지 않는다.**
→ `Args.state` 와 같은 구조다: **미리 선언하면 허용, 선언 없으면 에러.**

### 완벽한 정적 검사는 목표가 아니다

`__import__("ti"+"me")` 같은 우회는 **전부 막을 수 없다.**
**사전에 추측할 수 있는 행위만** 막고, 대신 **에러 메시지에 자연어 가이드를 넣는다.**
작성 주체가 AI 라는 전제 덕에 이게 유효하다 — 가이드를 읽고 고치면 되기 때문이다.

## 6.5 Library — 여러 스크립트가 나눠 쓰는 함수

**프로젝트 전체에서 "무엇이 버튼인가" 를 판정하는 함수는 하나여야 한다.**
그 함수 본체가 사는 자리가 라이브러리다.

**형제 파일 `import` 는 되지 않는다.** 스크립트 디렉터리는 `sys.path` 에 없고, 등록하면
스크립트 파일 하나만 복사되므로 옆 파일이 따라오지 않는다. 그래서 공유는 **등록소를 통해서** 한다.

### 왜 등록 종류인가 — 등록소가 이미 필요한 것을 전부 갖고 있다

| 원하는 것 | 등록소가 이미 하는 일 |
|---|---|
| 본체가 **단 하나** | 엔트리 하나 = 파일 하나 |
| 여러 스크립트가 참조 | 참조 그래프 |
| 본체를 고치면 쓰는 쪽이 안전한가 | **수정은 id 를 유지하고 상위를 전이적으로 재검증한다** |
| 몰래 못 고치게 | 실행 시 해시 대조 (`STR-REG-001`) |
| 안 쓰는 것·깨진 것 파악 | `list` 의 깨짐 표시 |

세 번째 줄이 핵심이다 — **판정 함수를 고치면 그것을 쓰는 모든 노드의 검증이 무효화된다.**
*"본체가 한 곳에 있다"* 가 실제로 의미를 갖는 이유가 이것이다.

**패키지로 만들어 설치하는 길(6절)도 여전히 유효하지만 성질이 다르다.** 그쪽은 **검증 경계 바깥**이라
해시도 없고 금지 패턴 검사도 안 받는다. 그 안에서 `import time` 을 하면 금지가 통째로 우회된다.
→ **프로젝트 고유의 판정 로직은 라이브러리로, 범용 서드파티는 패키지로.**

### 배선은 노드가 한다 — 선언/사용 분리 그대로

```jsonc
// 노드
{ "type": "perceive", "script": "${ref.sc_a1b2c3d4}",
  "libraries": { "buttons": "${ref.lb_9f8e7d6c}" } }
```

```python
# 스크립트
from strictler_lib import buttons
...
found = buttons.find_buttons(args.input.html)
```

| | 어디 | 무엇 |
|---|---|---|
| `from strictler_lib import buttons` | **스크립트** | **능력 선언** — "`buttons` 슬롯이 필요합니다" |
| `"libraries": { "buttons": … }` | **노드 JSON** | **사용 선언** — "그 슬롯엔 이걸 씁니다" |

1절의 선언/사용 분리와 그대로 겹친다. 새 개념이 늘지 않는다.

- 엔진이 로드 시점에 `strictler_lib.<이름>` 을 심는다. **네임스페이스를 쓰는 이유**는 같은 이름의
  실제 패키지를 가리는 사고를 막기 위해서다
- `script add` 는 스크립트만 보고 **필요한 슬롯 목록**을 계약에 기록한다
- `node add` 는 **슬롯이 전부 배선됐는지 + 그 참조가 실제로 라이브러리인지** 검사한다
- 스크립트 본문에 id 가 들어가지 않는다 — 참조는 JSON 에만 (2절 원칙 유지)
- 부수 효과: **스텁 라이브러리를 배선해 스크립트를 단위테스트**할 수 있다

### 라이브러리에도 정적 검사를 건다 — 단, 다른 것을

| | 스크립트 | 라이브러리 |
|---|---|---|
| 금지 패턴 (시간·랜덤·subprocess) | ✅ | ✅ **똑같이** |
| `runNode` / `Args` / 출력 타입 요구 | ✅ | ❌ 노드가 아니다 |
| 다른 라이브러리 `import` | (배선된 것만) | ❌ **금지 — 한 층만** |

금지 패턴을 라이브러리에 안 걸면 **거기서 `import time` 을 해 금지가 통째로 우회된다.**
라이브러리끼리 import 를 허용하면 그때부터 패키지 매니저를 만들게 된다.

### v1 의 경계 — 함수만. dataclass 선언은 하지 않는다

라이브러리는 **함수만** 제공한다. dataclass 를 선언하면 노드 간 계약 타입이 스크립트 밖에서
생기고, `extract_contract` 가 파일 하나만 파싱하므로 타입 레지스트리에 구멍이 난다.

타입 레지스트리가 이미 `TypeKey(origin, name)` 로 키를 잡고 **구조 동일성으로 부분집합 병합**을
하므로(7절) 원리적으로는 라이브러리를 또 하나의 origin 으로 등록하면 맞물린다. **그건 v2 다.**
실제로 답답한지 예제로 확인한 뒤에 연다 — 성급히 열었다가 타입 체계에 구멍이 나면 훨씬 비싸다.

**`strictler library test` 도 v1 에 두지 않는다.** 라이브러리엔 `runNode` 계약이 없어 지금
하네스가 그대로 맞지 않는다. 라이브러리는 그것을 쓰는 **노드 단위테스트를 통해 간접 검증**된다.

### "단 하나만 있을 수 있게" 는 강제하지 않는다 — 보이게 한다

이 메커니즘이 주는 것은 **본체가 하나인 것**이지, 누군가 스크립트 안에 같은 로직을 다시 인라인으로
쓰는 것을 막지는 못한다. 그걸 규칙으로 잡으려면 *"비슷한 함수인가"* 를 판정해야 하는데 오탐만 난다.

대신 **보이게** 한다 — `library show <id>` 가 그것을 쓰는 노드 전부를 보여주고,
`list` 가 아무도 안 쓰는 라이브러리를 표시한다. *"깨짐은 막지 않고 표시한다"* 와 같은 태도다.

## 7. 타입 시스템

**"표준 타입 같은 거 없다"는 *내장 의미 타입*(`Button` 같은 것)이 없다는 뜻이지,
타입 체계가 없다는 뜻이 아니다.** 오히려 **쓸 수 있는 타입을 강제해 범위를 좁힌다.**

### 쓸 수 있는 타입

| | 무엇 |
|---|---|
| **primitive** | `int` `float` `str` `bool` `bytes` `list[T]` |
| **노드 사전 선언 타입** | 복합 타입은 **무조건 `dataclass`**. C++ 의 `struct` 같은 자리 |

- **`dict` 금지** — 허용하면 "복합은 dataclass 강제"가 한 줄로 무의미해진다
- **`None` / `Optional` 금지** — "있을 수도 없을 수도"가 부분집합 규칙과 겹쳐 판정이 흐려진다
- `bytes` 는 스크린샷, `list[T]` 는 버튼 목록 때문에 필요하다

### ★ 두 층을 분리한다 — 여기가 핵심

| 층 | 대상 | 규칙 |
|---|---|---|
| **그래프 검사 (정적)** | **선언된 정의** | input 정의 **==** output 정의. **엄격한 동일성** |
| **데이터 취급 (런타임)** | **표현** | 부분집합 관계인 것들은 **상위 큰 dataclass 하나를 같이 써버린다** |

**부분집합 병합은 타입 검사를 느슨하게 만드는 것이 아니다.**
병합은 표현 층에서만 일어나고, 그래프 검사는 여전히 "같은 정의냐"만 본다.

**여분 필드가 비어 있어도 안전한 이유:**

```python
X: output A(count)          Z: input A(count)          # 그래프 검사 통과
Y: output B(count, label)   W: input B(count, label)
```

런타임엔 A·B 가 병합된 큰 클래스를 함께 쓴다. X 는 `count` 만 채우고 `label` 은 비어 있다.
**`label` 을 읽는 노드는 `B` 를 선언한 W 뿐이고, W 는 `B` 를 선언한 Y 하고만 연결된다** —
그래프 검사가 그걸 보장했다. → **비어 있는 필드에는 아무도 접근하지 않는다.**

→ 이게 `Optional` 금지와 충돌하지 않는 이유이기도 하다. 병합 클래스의 여분 필드가 비어 있을 수 있다는 건
   **표현 층의 구현 디테일**(미설정 센티널)이지, 스크립트가 **선언**하는 타입에 `Optional` 이 들어가는 게 아니다.

### 등록 시점에 집합 검사 한 번

엔진은 구성 시점에 **모든 노드의 dataclass 선언을 읽어 등록**하고 **집합 검사 로직을 전체로 건다.**
각 dataclass 를 **`(필드명, 타입)` 쌍의 집합**으로 다루면 별도 규칙이 필요 없어진다:

| | 왜 규칙이 필요 없나 |
|---|---|
| **필드 순서** | 집합이므로 애초에 의미가 없다 |
| **이름만 vs 이름+타입** | 원소가 `(이름, 타입)` 쌍이므로 자동 |
| **중첩 dataclass** | 중첩 필드의 타입도 등록된 dataclass 이므로, **위상 정렬해 바닥부터 정규화**하면 재귀가 저절로 된다 |

비용은 부분집합 비교 O(n²) 지만 n 이 노드 수준이라 무시할 크기다.

**병합 단위: 부분집합 격자의 연결 성분 전체를 합집합으로 병합한다.**
`A ⊂ B`, `A ⊂ C`, `B`·`C` 무관 — 이런 경우 "가장 큰 것"이 유일하지 않지만,
**그래프 검사가 선언된 정의로 이뤄지므로 어느 쪽으로 병합해도 정확성에 영향이 없다.**
연결 성분을 통째로 합집합 내면 모호함 자체가 생기지 않고 잃는 것도 없다.

### 오배선 탐지력은 약해진다 — 감수한다

```python
ButtonCount(count: int)  ==  MenuCount(count: int)
```

버튼 세는 노드의 출력을 메뉴 검증 노드에 꽂아도 그래프 검사를 통과한다. **감수한다:**
- 배선은 파이프라인 JSON 에 **노드 id 로 명시적으로** 쓰므로 타입 검사가 잡아주길 기대할 실수가 아니다
- 필드가 완전히 같으면 **기계적으로 안 깨진다**
- 값의 의미는 **Reckon 이 잡는다**

최소 필드 수 조건 같은 걸 넣으면 임의 상수가 되고, "이 타입은 고유하다" 표시를 주면
방금 없앤 명목 타입을 뒷문으로 들이는 것이다. 둘 다 안 한다.

## 8. 상태머신

```jsonc
"states": {
  "values": ["idle", "capturing", "settled"],
  "initial": "idle"
},

"transitions": [
  { "after": "startApiCapture", "to": "capturing" },
  { "after": "submitForm", "delay": "${config.settleMs}", "to": "settled" }
]
```

- **전이는 파이프라인 구동 엔진(별도 런타임 모듈)이 수행한다.** 상태는 파이프라인에 있으므로 파이프라인이 관리한다.
- **노드는 상태를 읽기만 한다**(`when`). 결과만 반환한다.
  → 재사용 노드가 남의 파이프라인 상태를 오염시킬 수 없고, 이름 매핑이 읽기 전용이라 단순해진다.
- `after` — 그 노드가 끝나면. `delay` — 그 뒤 지연.
- **`transitions` 는 시간만 다룬다.** 노드 결과에 따른 분기 문법은 **존재하지 않는다**(10절).

### 상태 이름은 파이프라인마다 다르다

노드는 자기 어휘로 필요 상태를 선언(`Args.state` 의 필드 이름)하고, 파이프라인의 노드 `states` 가 이름 매핑을 갖는다.
→ 노드를 파이프라인 간에 그대로 재사용할 수 있다.
→ 로드 시점에 **매핑 누락·존재하지 않는 상태 참조를 잡는다.**

### state 는 "엔진의 실행 상태" 하나다

`capturing` 같은 사용자 정의 상태와 실행 시각 같은 엔진 제공 값은 **성질이 다른 두 가지가 아니다.**
둘 다 **엔진의 실행 상태**이고, `Args.state` 라는 **하나의 dataclass 안의 필드들**이다.
필드마다 타입이 다른 건 dataclass 가 이미 처리한다.

- 실행 시각은 **엔진이 자동으로 채워주는 필드**다. 사용자가 `states.values` 에 선언하지 않는다.
- **`__` 접두는 엔진 제공 필드 예약** — `${state.__startedAt}`. 사용자 상태 이름에 `__` 접두 **금지**.
- 형식은 **epoch 밀리초 정수**. 문자열 포맷을 주면 스크립트가 파싱하다가
  로케일·타임존 비결정성이 새어들어온다.

## 9. ★ 이건 lint 다 — 결과 상태와 실패 처리

**"실패"도 하나의 정상적인 상태다.** 위반을 찾아낸 것은 사고가 아니라 **lint 가 제 일을 한 것**이다.

→ **"실패했을 때 무엇을 해야 하나"라는 사고를 하지 않는다.**
  복구·재시도·되돌아가기·대체 경로 — 전부 실행 엔진의 사고방식이고 여기 해당 없다.

| 상태 | 성격 |
|---|---|
| **통과** | 정상 |
| **위반** | 기획과 다르다 — **정상 결과.** 리포트에 담긴다 |
| **not run** | 앞단 실패의 여파로 도달 불가 — **정상 결과.** 통과와 구분해 보고 |
| **오류** | 스크립트 예외, 계약 위반, 경로 없음, 환경변수 미정의 — **비정상. 도구가 못 돈 것** |

**고쳐야 할 것은 오류뿐이다.** 이 구분이 흐려지면 위반을 오류처럼 다루거나(불필요한 복구 로직),
오류를 위반처럼 다루게 된다(거짓 리포트).

### 실패는 최대한 수집하고, 여파는 not run

- **한 번의 실행에서 확인 가능한 실패를 전부 모은다.**
- 한 `plan` 항목이 실패해도 **다른 항목은 전부 돈다.**
- 실패 지점의 **뒷단을 억지로 이어가지 않는다** — 이어가면 **실패가 전파되어** 원인이 뭉개진다.

**전파 경로가 둘이다:**

| 경로 | 내용 |
|---|---|
| **데이터 의존** | 실패한 노드의 출력을 `inputs` 로 받는 노드들 |
| **상태 의존** | **상태를 변경할 노드가 실패하면**, 그 상태에 조건이 걸린 노드들도 `not run` |

두 번째를 놓치기 쉽다. `transitions` 의 `after` 가 실패하면 그 전이가 일어나지 않고,
그 상태를 `when` 으로 기다리던 노드들은 영원히 조건을 만족하지 못한다.

→ **not run 표기 시 노드를 전수 검사한다.** 도달 불가가 된 것을 싹 다 바꾼다.

### 증거 캡처는 하지 않는다

위반 시 화면을 캡처해 근거로 남기는 기능은 넣지 않는다.
이유는 "번거로워서"가 아니라 **위반은 정상 결과이므로 수습할 것이 없기 때문**이다.
lint 가 스크린샷을 남기지 않는 것과 같다.

## 10. 조건 분기 — 엔진 문법이 없다

**분기는 스크립트가 그냥 `input` 을 반환하는 것으로 표현한다.**
*"앞단 결과가 이러면 나는 아무것도 안 하고 그대로 흘려보낸다."*

**엔진에는 skip 개념이 없다.** 엔진은 평소대로 input/output 타입만 검사하고,
**타입을 맞추는 건 스크립트 책임**이다.

→ `skipWhen` 같은 필드도, 전이 조건 표현식 언어도 필요 없다.
→ 결과 상태 집합에도 skip 이 없다 (9절).

## 11. 리포트

**flat 리스트 + 경로 필드.** Spec→plan→pipeline→node 중첩으로 쌓지 않는다 —
기계가 읽기 쉽고 AI 가 고치기 쉬운 쪽을 택한다. **요약 헤더에 4상태 카운트를 낸다.**

```jsonc
{
  "summary": { "pass": 12, "violation": 2, "not_run": 3, "error": 1 },
  "results": [
    { "path": "login.json > plan[0] > login-flow", "node": "detectButtons",
      "status": "violation", "rule": "expectedCount",
      "message": "버튼 3개 기대, 2개 관측" },

    { "path": "login.json > plan[0] > login-flow", "node": "checkToken",
      "status": "not_run",
      "cause": { "node": "captureHtml", "reason": "state_unreachable" } },

    { "path": "login.json > plan[1] > menu-check", "node": "detectMenu",
      "status": "error", "rule": "STR-N002",
      "message": "runNode 의 인자 타입 `Args` 가 선언돼 있지 않습니다. 모든 노드 스크립트는 `Args` 라는 이름의 dataclass 를 정의하고 runNode(args: Args) 형태여야 합니다." }
  ]
}
```

- **가이드는 별도 필드가 아니라 에러 메시지에 포함**한다.
- **`not_run` 의 원인 노드는 not run 으로 바꾸는 그 시점에 적는다** (9절의 전수 검사 시점).
- 리포트 누적 단위는 **노드별**이다.

## 12. 비교 파이프라인

`kind: "compare"` 일 때만 쓰는 두 섹션.

```jsonc
"targets": ["legacy", "v2", "v3", "canary"],   // 비교 대상 — 개수 제한 없음
"compare": ["detectButtons", "extractMenu"]    // 어느 노드의 출력을 비교하나
```

### ★ target 별로 갈리는 것 — 스크립트와 그 값

**노드도 그래프도 한 벌이다.** 동일 노드를 여러 벌의 형상에 적용하는 것이고,
**target 별로 갈리는 것은 스크립트와 그 스크립트가 쓰는 값(`params`) 뿐이다.**

| | 갈리나 | 왜 |
|---|---|---|
| **`Args.input` 타입 / 출력 타입** | **공통** | **파이프라인 구동 개념**이다. 노드에 귀속되므로 target 간에 다를 수가 없다 |
| **`Args.state`** | **공통** | 같은 이유 — 파이프라인 상태를 참조하는 것이므로 |
| **`script` 경로** | **갈림** | 인식 방법이 A/B 마다 다른 것이 설계다 |
| **`Args.params`** | **갈림** | **스크립트가 갈라지니 거기 필요한 값도 갈라진다.** 타입도 값도 |

```jsonc
// nodes/detect_buttons.json — 노드는 하나
{ "type": "perceive", "script": "${config.buttonScript}" }
```
```jsonc
// Spec 의 config — 스크립트와 그 값이 target 별로
"config": {
  "settleMs": 2000,                                    // 공통
  "targets": {
    "legacy": {
      "buttonScript": "${env.PROJECT_ROOT}/scripts/legacy_buttons.py",
      "classPrefix": "btn-"                            // 이 스크립트만 쓰는 값
    },
    "v2": {
      "buttonScript": "${env.PROJECT_ROOT}/scripts/v2_buttons.py",
      "roleAttr": "data-role"
    },
    "v3": {
      "buttonScript": "${env.PROJECT_ROOT}/scripts/v3_buttons.py",
      "roleAttr": "aria-role"
    },
    "canary": {
      "buttonScript": "${env.PROJECT_ROOT}/scripts/v3_buttons.py",   // 스크립트 공유도 가능
      "roleAttr": "aria-role"
    }
  }
}
```

**config 해석 규칙:** target `T` 로 도는 동안 `${config.X}` 는
**`targets.T` 에서 먼저 찾고, 없으면 공통에서** 찾는다.

→ **A 와 B 의 인식 스크립트가 다른 것이 설계**라는 원칙이 여기서 구현된다.
   각자 개념 레벨까지 올린 뒤 그 층위에서 비교하므로 **HTML 이 완전히 달라도 개념이 같으면 통과**한다.
→ **비교가 성립하는 근거는 input/output 타입이 노드에 귀속되어 공통이라는 것**이다.
   (등록 시 target 별 스크립트들이 같은 input/output/state 타입을 선언했는지 검사한다 — 13절)

### 실행 방식 — 노드가 내부적으로 A·B 를 돌리고 취합해 넘긴다

```
        detectButtons              extractMenu
        ┌──────────────┐           ┌──────────────┐
        │ legacy 스크립트│           │ legacy 스크립트│
        │ v2     스크립트│──▶{ legacy,│ v2     스크립트│──▶{ legacy, ─▶ …
        │ v3     스크립트│    v2, v3,│ v3     스크립트│    v2, v3,
        │ canary 스크립트│    canary }│ canary 스크립트│    canary }
        └──────────────┘           └──────────────┘
```

1. 노드가 실행되면 **내부적으로 target 별 스크립트를 각각 실행**한다.
2. **결과 전부를 취합해서 다음 노드로 넘긴다.**
3. 다음 노드는 그 묶음을 input 으로 받아 **target 마다 자기 스크립트를 또 실행**한다.

**취합/분배는 엔진이 한다.** 스크립트는 자기 target 의 값 하나만 받고 하나만 내놓는다.
→ **스크립트의 모양이 값 검증 파이프라인과 완전히 같다.** 비교용이라고 시그니처가 달라지지 않는다.

### 비교와 Verdict — 목록 전부가 같아야 통과

**`targets` 개수에 제한이 없다.** 2개도 되고 열 개도 된다.

**위반 판정은 단순하다: `targets` 에 넣어놓은 목록이 전부 같은 값을 뱉지 않으면 위반이다.**
"둘을 짝지어 비교"가 아니라 **전체가 한 값으로 일치하느냐**를 묻는다. 하나만 어긋나도 위반.

- `compare` 에 적힌 노드의 취합 결과가 target 간 **완전히 동일한지 엔진이 비교**한다.
- **Reckon 이 필요 없다** — Verdict 를 엔진이 만든다.
  "내장 동작 없음" 원칙과 충돌하지 않는다: **동등 비교는 도메인 지식이 아니라 일반 연산**이다.

**비교는 `Percept` 층에서 한다.** `Sensum` 은 비교 대상이 아니다 —
구조 리팩터링을 하면 HTML 은 완전히 달라지고, 잡으려는 건 **개념 층이 같은지**다.

**"동일하다"는 정말로 동일하다는 뜻이다.** 허용 오차도 무시 필드도 엔진에 두지 않는다.
**정규화는 비교용 데이터를 출력하는 노드의 스크립트가 알아서 한다** — 좌표 반올림, 타임스탬프 제거 등.
무엇을 무시해도 되는지는 도메인 지식이고, 도메인 지식은 언제나 스크립트 쪽에 있다. **엔진은 `==` 만 안다.**

### 리포트는 별도 형식

값 검증은 **노드별 판정**이고 비교는 **노드별 대상 간 대조**라 필드가 안 겹친다. 섞지 않는다.

```jsonc
{ "detectButtons": { "same": false,
    "values": { "legacy": 3, "v2": 3, "v3": 2, "canary": 3 } } }
```

**출력 위치는 Spec 의 `plan` 항목 `report`** 에 지정하고, 파이프라인이 실행과 동시에 쌓는다.
→ "증거 캡처는 하지 않는다"와 모순되지 않는다. 그건 *위반 후 사후 수습*을 거부한 것이고,
  이건 **실행과 동시에 쌓는 산출물**이다. 성격이 다르다.

## 13. 검사 시점과 검증 항목

### ★ 검사는 등록/수정 시점에 한다

**노드 검사와 파이프라인 검사는 등록·수정 시점에 돈다.**
검사에 걸리면 **명확한 에러를 뱉고 등록/수정이 실패**한다. 잘못된 것이 저장되지 않는다.

| 시점 | 대상 | 실패하면 |
|---|---|---|
| **노드 등록** | 노드 JSON + 그 스크립트 | **등록 실패** — 저장되지 않는다 |
| **파이프라인 등록** | 파이프라인 JSON + 참조된 노드들 | **등록 실패** |
| **Spec 실행** | config 채움 + 경로 전개 + `tool` + **해시 대조** | 실행 실패 |

**수정 시점이 따로 없다** — 수정이 없고 등록·삭제뿐이다 (2절).
실행 시 **등록소 파일의 해시가 등록 당시와 같으면 정적 검사를 다시 하지 않는다.**
경로로 직접 참조한 미등록 파일만 전수 검사한다.

→ AI 저작 워크플로우의 안전망이 여기 있다. **잘못 쓴 순간 걸리고, 돌려보기 전에 자기 수정한다.**

### 노드 등록 시

| 검증 | 근거 |
|---|---|
| `script` 가 실재하는지 (`${ref.sc_...}` 또는 경로), 경로 규칙을 지키는지 | 참조 무결성 / 경로 규칙 |
| `${ref.<id>}` 의 접두가 그 자리가 요구하는 종류와 맞는지 | 등록소 |
| 스크립트가 `runNode(args: Args)` / `returnResult()` 형태인지, `Args` 가 선언됐는지 | 노드 계약 |
| `Args` 필드가 `input`/`params`/`state` 중에서만 쓰였는지 | `Args` 규약 |
| 선언된 타입이 primitive 집합 + dataclass 뿐인지 (`dict`·`Optional` 금지) | 타입 시스템 |
| `type` 이 Reckon 이면 `Args.params` 에 기댓값 필드가 있는지 | 기획 껍데기화 방지 |
| `type` 이 Action 이면 input 타입 == output 타입인지 | Action 계약 |
| 금지 패턴(시간·랜덤·직접 subprocess·미선언 state)이 없는지 | 금지 목록 |
| `Args.state` 필드 이름에 `__` 접두를 사용자가 쓰지 않았는지 | 예약 네임스페이스 |

### 파이프라인 등록 시

| 검증 | 근거 |
|---|---|
| `source` 가 가리키는 노드가 등록소에 있는지 (또는 파일이 실재하는지) | 참조 무결성 |
| `${ref.<id>}` 의 접두가 그 자리가 요구하는 종류와 맞는지 | 등록소 |
| `inputs` 가 가리키는 노드 id 가 실재하는지 | 참조 무결성 |
| DAG 에 순환이 없는지 | DAG |
| 등록된 dataclass 집합 정규화 후 **input 정의 == output 정의**인지 | 타입 시스템 |
| 노드의 `states` 매핑이 빠짐없고, 매핑 대상이 `states.values` 에 실재하는지 | 상태 이름 매핑 |
| `when` 이 참조하는 상태 id 가 스크립트의 `Args.state` 에 선언됐는지 | 상태 매핑 |
| **`when` 이 참조하는 상태로 가는 transition 이 존재하는지** | **도달 가능성** |
| **조건과 그래프만으로 상태머신을 돌려 안 닿는 노드가 없는지** | **도달 가능성** |
| `transitions.after` 가 실재 노드 id 인지, `to` 가 실재 상태인지 | 상태머신 |
| 사용자 상태 이름에 `__` 접두가 없는지 | 예약 네임스페이스 |
| `config` 선언의 `type` 이 primitive 집합에 속하는지 | 타입 어휘 통일 |
| `kind: compare` 일 때 `compare` 가 가리키는 노드가 실재하는지 | 비교 선언 |
| `kind: compare` 일 때 **각 노드의 target 별 스크립트가 같은 input/output/state 타입을 선언했는지** (`params` 는 달라도 됨) | **비교 계약** |

**도달 가능성 검사가 핵심이다.** `when` 이 영원히 참이 안 되는 노드는 실패도 아니고 not run 도 아니라
4상태 어디에도 안 들어간다 — **정적으로 잡아 등록 자체를 막는다.**
조건과 그래프만으로 상태머신을 돌려보면 정적으로 판정된다.

### Spec 실행 시

| 검증 | 근거 |
|---|---|
| `config` required 가 다 채워졌는지, 타입이 맞는지 | config 선언 |
| 모든 경로가 전개 후 절대경로인지, 참조 환경변수가 정의됐는지 | 경로 규칙 |
| `path: true` 인 config 값이 경로 규칙을 지키는지 | 경로 규칙 |
| `tool` 미선언 함수·실행파일 경로를 쓰지 않는지 | `tool` |
| `kind: compare` 인데 `report` 가 없으면 에러 | 종류별 필수 필드 |
| **등록소 파일의 해시가 등록 당시와 같은지** | **등록소 무결성** |
| **참조하는 id 가 삭제되지 않았는지** | **등록소 무결성** |

## 14. 노드 단위테스트

**기본 제공 타입검사 + 사용자 커스텀 단위테스트.** 별개 기능이 아니라 **같은 실행의 두 층위**다.

| | 무엇을 보나 | 사용자가 쓰는 것 |
|---|---|---|
| **기본 제공** | 돌려서 **타입이 맞는지** | 입력 fixture 만 |
| **커스텀** | 돌려서 **값이 맞는지** | 입력 fixture + 기대 출력 |

→ **기대값을 안 써도 타입 검증은 공짜로 따라온다.** 그게 "기본 제공"의 의미다.
→ 입력 fixture 는 어느 쪽이든 필요하다. 안 주면 돌릴 수가 없다.

### 등록 검사와 다른 것

| | 스크립트를 | 잡는 것 |
|---|---|---|
| **등록/수정 시 검사** (13절) | **안 돌린다** | 선언·형식·금지 패턴 |
| **단위테스트** | **돌린다** | 선언한 대로 실제로 동작하는가 |

등록 검사는 "`Args` 를 선언했나"를 보고, 단위테스트는 "선언한 타입이 실제로 나오나"를 본다.
**pydantic 경계 검증이 실제 값을 만나는 유일한 자리**가 여기다.

### 파일 형태 — `<노드파일>.test.json`

노드 파일을 두껍게 하지 않으므로 **별도 파일**이다.

```jsonc
// nodes/detect_buttons.test.json
{
  "node": "${env.PROJECT_ROOT}/nodes/detect_buttons.json",

  "cases": [
    {
      "name": "버튼 3개짜리 평범한 페이지",
      "args": {
        "input":  { "html": "<div><button>확인</button>…</div>" },
        "params": { "expected": 3 }
      },
      "expect": { "count": 3, "labels": ["확인", "취소", "닫기"] }
    },
    {
      "name": "버튼 없는 페이지 — 타입만 확인",
      "args": {
        "input":  { "html": "<div></div>" },
        "params": { "expected": 0 }
      }
      // expect 없음 → 기본 타입검사만 돈다
    }
  ]
}
```

- `args` 는 **`Args` dataclass 를 JSON 으로 그대로 쓴 것**이다. **별도 문법이 없다** —
  dataclass 필드가 primitive + 중첩 dataclass + `list[T]` 뿐이라 JSON 으로 정확히 표현된다.
- `expect` 는 **출력 dataclass 를 JSON 으로 쓴 것**. 생략하면 타입만 본다.
- **`bytes` 필드**(스크린샷 등)는 JSON 에 못 담으므로 **파일 경로로 준다** —
  `{ "$file": "${env.PROJECT_ROOT}/fixtures/shot.png" }`. 엔진이 읽어 bytes 로 채운다.
  경로 규칙 그대로 적용.

### 기본 제공이 확인하는 것

케이스마다 순서대로:

| | 확인 | 실패하면 |
|---|---|---|
| 1 | `args` 가 스크립트의 `Args` 선언에 맞는가 | **테스트 정의가 잘못됨** |
| 2 | `runNode` 가 예외 없이 끝나는가 | 오류 |
| 3 | `returnResult()` 반환값이 선언된 출력 타입에 맞는가 | 오류 |

**1번을 따로 세는 이유:** 스크립트가 아니라 **테스트 쪽이 틀린 경우**라 에러 메시지가 달라야 한다.
AI 가 fixture 를 잘못 썼는지 스크립트를 잘못 썼는지 구분되어야 자기 수정이 된다.

### 노드 타입별로 추가되는 기본 검사

**Action — 값 동일성까지 본다.**
`input == output` 이 계약이므로 **타입이 아니라 값이 같은지**를 자동 검사할 수 있다.
사용자가 `expect` 를 안 써도 된다 — **기대값이 곧 입력**이기 때문이다.

**Reckon — 기댓값 반응성.**
"기댓값 하드코딩 금지"는 정적으로는 `Args.params` 에 필드가 **있는지**까지만 본다.
받아놓고 안 쓰면 못 잡는다. 단위테스트는 이걸 **동적으로 잡는다.**

단, 값을 흔들어보는 것만으론 안 된다 — `expected=3` 도 `expected=4` 도 실제가 2개면 둘 다 위반이라
결과가 같게 나온다. **통과하는 기댓값과 위반하는 기댓값이 둘 다 있어야** 반응성이 증명된다.

→ 규칙: **Reckon 노드의 테스트는 `input` 이 같고 `params` 만 다른 "통과 케이스 + 위반 케이스" 쌍을
  최소 하나 가져야 한다.** 없으면 **경고**, 있는데 판정이 같으면 **오류**.
  (강제가 아니라 경고인 이유: 규칙 위반이 아니라 테스트 커버리지 문제에 가깝다)

### 결정성 검사는 하지 않는다

같은 입력으로 두 번 돌려 같은 결과가 나오는지 보는 건 값싸고 강력하지만,
**Perceive 안에서 AI 를 부르면 당연히 실패한다.**
**"노드 내부는 input/output 만 맞추면 된다"와 정면으로 충돌**하므로 하지 않는다. (15절)

### 등록 시 테스트를 요구하지 않는다 — 별도 명령이다

```
strictler register-node <node>   → 정적 검사. 통과해야 등록됨
strictler test-node <node>       → 실제 실행. 명시적으로 돌린다
```

이유 둘:
- 단위테스트는 **스크립트를 실제로 돌리므로** Vantage·Sense 라면 playwright 같은 외부 도구가
  실제로 뜬다. 등록이 무거워지고 환경 의존이 생긴다.
- 등록 검사는 "형식이 맞나"이고 테스트는 "동작이 맞나"라 **실패의 성격이 다르다.**

저작 워크플로우는 **등록으로 형식을 잡고 → 테스트로 동작을 잡고 → 파이프라인에 연결**하는 순서가 된다.
"통짜로 돌려 실패하면 AI 가 원인을 특정할 수 없다"는 문제가 이 순서로 풀린다.

### ★ Perceive 스크립트 검사 카테고리를 이것이 흡수한다

`.test.json` 이 하는 일이 정확히 *"이 HTML 을 주면 버튼을 3개로 인식하는가"* 이고,
그게 곧 **Perceive 스크립트가 개념을 제대로 인식하는가**를 묻는 것이다.

→ **별도 파이프라인을 짤 필요가 없다.** 원래 "같은 스키마·같은 엔진으로 대상만 Perceive 스크립트로
  바꿔서 검사한다"고 했는데, **더 싼 자리가 이미 있었다.**

| 카테고리 | 어디서 |
|---|---|
| 프로그램 검사 | Spec 실행 |
| **Perceive 스크립트 검사** | **노드 단위테스트** |

## 15. 전체 예시 — 로그인 검증

```jsonc
// pipelines/login-flow.json
{
  "info": { "name": "login-flow", "description": "로그인 동작 검증", "kind": "verify" },

  "config": {
    "loginUrl":   { "type": "str", "required": true },
    "settleMs":   { "type": "int", "required": false, "default": 2000 },
    "tokenShape": { "type": "str", "required": true }
  },

  "states": { "values": ["idle", "capturing", "settled"], "initial": "idle" },

  "transitions": [
    { "after": "startApiCapture", "to": "capturing" },
    { "after": "submitForm", "delay": "${config.settleMs}", "to": "settled" }
  ],

  "nodes": [
    { "id": "page", "source": "${env.PROJECT_ROOT}/nodes/browser_goto.json",
      "params": { "url": "${config.loginUrl}" } },

    { "id": "captureHtml", "source": "${env.PROJECT_ROOT}/nodes/html.json",
      "inputs": { "scene": "page" } },

    { "id": "startApiCapture", "source": "${env.PROJECT_ROOT}/nodes/net_start.json",
      "inputs": { "scene": "page" } },

    { "id": "detectForm", "source": "${env.PROJECT_ROOT}/nodes/detect_form.json",
      "inputs": { "html": "captureHtml" } },

    { "id": "submitForm", "source": "${env.PROJECT_ROOT}/nodes/fill_and_submit.json",
      "inputs": { "form": "detectForm" } },

    { "id": "endApiCapture", "source": "${env.PROJECT_ROOT}/nodes/net_end.json",
      "inputs": { "handle": "startApiCapture" },
      "states": { "stop": "settled" },
      "when": { "state": "stop" } },

    { "id": "extractToken", "source": "${env.PROJECT_ROOT}/nodes/extract_token.json",
      "inputs": { "traffic": "endApiCapture" } },

    { "id": "checkToken", "source": "${env.PROJECT_ROOT}/nodes/token_valid.json",
      "inputs": { "token": "extractToken" },
      "params": { "expected": "${config.tokenShape}" } }
  ]
}
```

읽으면: 페이지 열기 → HTML 수집 / 네트워크 캡처 시작 → 폼 검출 → 입력·제출(Action) →
2초 뒤 `settled` → 그때 캡처 종료 → 토큰 추출 → 토큰 판정.

`submitForm` 은 Action 이므로 `detectForm` 의 출력을 **그대로 통과**시킨다.

## 16. 폐기된 안 — 다시 꺼내지 말 것

| 폐기 | 왜 |
|---|---|
| **프로그램 → 기획 추출** | 형상에서 기획을 역으로 뽑는 방법이 없다. 함께 사라진 것: provenance 구분, VRT 퇴화 위험, **"스키마가 기계 생성 가능해야 한다"는 제약** |
| **노드 `skipWhen` / skip 전파 / 노드 상태 `skipped`** | skip 은 엔진 개념이 아니다. 스크립트가 `return input` 할 뿐 (10절) |
| **전이 조건 표현식 언어** | 이건 lint 다. "실패했으니 다른 경로로"가 없다 |
| **"구간형 Sense 를 상태+condition 으로"** | 그냥 Sense 두 개다. 특수 문법이 애초에 불필요했다 (5절) |
| **"Action 은 output 이 없다"** | output 이 있고 input 과 동일하다 (5절) |
| **"Perceive·Reckon 은 순수해야 한다"** | 순수성 개념을 두지 않는다. 노드 내부는 input/output 만 맞추면 된다 (6절) |
| **노드 타입별 파일 IO·네트워크·환경변수 금지** | 위와 함께 소멸. 금지는 전 노드 균일 (6절) |
| **`def reckon(percept, expected)` 시그니처** | 진입점은 전 타입 `runNode(args)`. 제약은 `Args.params` 필드 요구로 (6절) |
| **바인딩 기제 3종 통일** | 층이 다르다. `${config.X}` 참조 문법만 공유 (1절) |
| **서브그래프 재사용 문법** | 노드가 별개 파일이므로 재사용은 근본 동작 (1절) |
| **노드 파일을 두껍게** | 역할 분리의 결과이지 빈 자리가 아니다 (1절) |
| **증거 캡처(스크린샷)** | 위반은 정상 결과라 수습할 것이 없다 (9절) |
| **사용자 코드 샌드박싱** | ESLint·vite·jest 전부 사용자 코드를 그냥 로드해 실행한다. lint 계열 표준 신뢰 모델을 따른다 |
| **단위테스트 결정성 검사(2회 실행 비교)** | Perceive 안에서 AI 를 부르면 당연히 실패한다. "노드 내부는 input/output 만 맞추면 된다"와 충돌 (14절) |
| **Perceive 스크립트 검사 전용 파이프라인** | 노드 단위테스트가 흡수한다. 더 싼 자리가 이미 있었다 (14절) |
| **BeautifulSoup** | lxml 백엔드로도 13배 느리다. selectolax(lexbor) 권장 |
| **MCP 서버** | CLI 가 `--json` 과 종료 코드 `0`/`1`/`2` 로 같은 정보를 이미 준다. 상주 서버는 one-shot 프로세스 모델과 어긋나고, **표면이 둘이면 계속 어긋난다** — 이 프로젝트에서 CLI 하나로도 배선 결함이 났다. 셸을 못 쓰는 클라이언트가 실제로 생기면 그때 CLI 를 얇게 감싼다 |

## 17. 남은 미결

**스키마 층에는 없다.** 열려 있던 질문은 전부 닫혔고, **구현도 끝났다** —
등록소·검사기·실행 엔진·단위테스트 하네스·CLI 가 전부 서 있고 예제가 CLI 로 끝까지 돈다.
구현 결과 드러난 계약 결함과 그 판정은 [`MODULES.md`](MODULES.md) 의 **계약 개정 R1~R6** 에,
규칙이 늘어난 경위는 [`rules.md`](rules.md) 의 **증가 이력**에 있다.

### 열어둔 것

**없다.** 마지막까지 열려 있던 둘 — 노드 스크립트의 의존성 격리와 해시 재사용 — 은
각각 6절(**격리하지 않는다. 등록 시점에 확인만 한다**)과 2절(**해시가 같으면 재검사하지
않는다**)로 확정됐고 구현됐다.
